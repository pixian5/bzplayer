## 一、审查动机

首轮修复只解决了"ffprobe 可用"这一条路径。对改动做代码审查后，发现它在其它路径下仍会失效，故补齐四项。

## 二、实测证据（本轮新做）

原始样本已改名，另用 ffmpeg 合成等价样本 `/tmp/probe_mp3_in_mp4.mp4`（`h264/avc1` + `mp3/mp4a`，与原文件特征一致），用 `AVURLAsset` 实测：

```
audioTracks = 0     videoTracks = 1 (avc1)     isPlayable = true
```

**关键含义**：音轨被静默丢弃，但文件仍被判为"可播"。因此**不会触发任何"播放失败自动回退"**，用户侧表现为"能放、没声、不报错"。这决定了必须在**路由阶段**判出，不能依赖运行时回退。

另确认：ffprobe 是**外置可选依赖**（`MediaAnalyzer.toolInvocation` 只查 `/opt/homebrew/bin`、`/usr/local/bin`、`/usr/bin`，应用不内置）。

## 三、审查发现的四个问题与修复

| # | 问题 | 修复 |
|---|---|---|
| 1 | **ffprobe 缺失时修复完全失效**：`shouldPreferVLC(asset:)` 的兜底遍历 `audioTracks`，而实测 `audioTracks=0`，循环体根本不执行 | 新增 `mp4FamilyAudioNeedsVLC(url:ffprobeInfo:)`：ffprobe 缺失且容器属 MP4 系列时，以"音轨为空"为信号走 VLC |
| 2 | **AV1 早退绕过音频检查**：`chooseBackend` 中 `if hasAV1 { return .native }` 排在所有音频判断之前，AV1 + MP3-in-MP4 会漏判成原生、静音 | 把"MP4 系列 + 不安全音频"判断**提到 AV1 分支之前**；AV1 的原生优先策略保留不变 |
| 3 | **重复加载**：`shouldPreferVLC(asset:)` 对同一批音轨两次 `await load(.formatDescriptions)` | 一次性收集 `audioSubtypes`，白名单判断与 MP3 判断共用同一次加载 |
| 4 | **不安全集合过窄**：只含 `mp3`，MP4 内的 `mp1`/`mp2` 有同样盲区 | `BackendRoutingCore.mp4FamilyUnsafeAudioCodecs = ["mp3", "mp1", "mp2"]` |

### 附带重构：判据下沉到 Core（为可测）

原来"MP4 系列容器 + mp3"的判据写在 `PlayerViewModel`（App target，`private`，无法单测）。本轮抽出纯逻辑到 **`Sources/BZPlayerCore/BackendRoutingCore.swift`**：

- `BackendRoutingCore.isMP4FamilyContainer(_:)` —— mp4/m4v/m4a/3gp/3g2/f4v，大小写不敏感
- `BackendRoutingCore.mp4FamilyAudioNeedsVLC(containerExtension:audioCodecs:)`

`PlayerViewModel` 改为调用 Core，删除本地重复定义，消除两处规则各自漂移的风险。

### 修改后的路由顺序（`chooseBackend`）

1. 非原生容器（mkv/avi/webm…）→ `.vlc`
2. `audioDelayMs != 0` → `.vlc`
3. **「MP4 系列容器 + 不安全音频」→ `.vlc`**（新增，位于 AV1 之前）
4. `hasAV1` → `.native`（硬件解码省电，策略不变）
5. ffprobe 可用 → `shouldPreferVLC(ffprobeInfo:)`；h264 解码错误 → `.vlc`
6. ffprobe 缺失 → `shouldPreferVLC(asset:)`
7. 默认 → `.native`

## 四、取舍与已知代价

- 第 1 项的兜底信号是"MP4 系列容器 + 音轨为空"。**代价**：真正无音轨的 MP4（如无声录屏）在 ffprobe 缺失时也会走 VLC——VLC 能正常播放，仅功耗略高；换来的是不会静音。仅在 ffprobe 不可用时生效，不影响常规路径。
- 纯 `.mp3` 文件（容器非 MP4 系列）**不受影响**，仍走原生——已由单测锁住，防止误伤。

## 七、追加：把路由顺序变成可测纯函数（00:35 补）

上一版只把"容器 × 编码"判据下沉到 Core，`chooseBackend` 的**短路 return 顺序**仍无法单测。
本轮再把顺序本身抽成 Core 的纯函数 `BackendRoutingCore.decide(...)`，返回三态 `RoutingDecision`：

- `.vlc` / `.native`：前置规则已确定
- `.needsFurtherProbe`：需调用方继续异步探测（h264 解码错误扫描、ffprobe 缺失时的 AVAsset 探测）

`chooseBackend` 退化为"准备入参 + switch"，语义与原先完全一致（AV1 仍短路走原生，仍优先于 ffprobe 的判断）。
新增 8 个顺序单测，重点锁住 **AV1 + MP3-in-MP4 → `.vlc`**（曾因 AV1 早退而漏判静音）。
