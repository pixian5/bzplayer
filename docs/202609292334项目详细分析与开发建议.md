## 二、做得好的地方（建议保持）

1. **双后端路由 + 代次（generation）机制**：`mediaOpenGeneration` / `activeSeekGeneration` 等机制虽然复杂，但有效隔离了异步回调错乱，是竞态修复史（多次提交记录）沉淀下来的成果，重构时必须保留语义。
2. **VLCKit 依赖管理成熟**：本地 path package + `VLCKIT.lock`（版本/URL/SHA256/大小四要素校验）+ 861 MB 归档缓存 + [VLC4_MAINTENANCE.md](file:///Users/x/code/bzplayer-main/docs/VLC4_MAINTENANCE.md) 单一操作入口，升级流程文档化。
3. **构建—安装—部署闭环**：`build_macos_app.sh` / `install_macos_app.sh` / `deploy.sh` 三脚本职责清晰；`--commit` 显式提交设计避免了误提交；安装脚本会强制结束旧进程、重建 .app、`lsregister` 刷新并启动。
4. **持久化写入做了异步化**：`JSONWriteQueue` 单队列串行写 + `.atomic`，退出时 flush，避免主线程 IO。
5. **工程细节完整**：全屏/画中画之外的常见播放器行为（睡眠断言、鼠标空闲隐藏光标、控制栏自动隐藏、进度节流 5 秒）都有处理。

## 三、主要问题（按优先级排序）

### P0-1 PlayerViewModel 是 God Object（3466 行，且仍在增长）

**证据**

- 单文件承载 **10+ 职责**：播放控制、后端管理、播放列表、全局/文件级设置持久化、字幕、窗口行为、媒体分析（ffprobe/ffmpeg）、音频延迟、最近文件、格式关联、基准测试。
- **53 个 `@Published` 属性**，任何一次 `currentTime`（0.5 s 一次）更新都会触发所有订阅视图重新求值。
- 8 月两份方案文档（`qwen开发方案.md`、`seed开发方案.md`）已建议拆分，**未执行**；当时记录约 2630 行，现在 3466 行（**净增 836 行**），说明新功能仍在持续堆入。

**影响**

- 修改任何功能都需要在 3466 行里定位，容易引入回归；历史提交中"修复 X 引入 Y"的模式（多次竞态修复提交）与之直接相关。
- 无法对核心状态机（seek generation、后端切换/回退、audio-only 切换）写单元测试。
- 多窗口场景每个窗口一个 ViewModel 实例，但静态缓存（`fileSettingsCache`、`settingsCache`）为共享全局，隔离边界模糊。

**建议（分阶段，避免大爆炸重构）**

| 阶段 | 内容 | 产出 |
|------|------|------|
| A | 把纯数据逻辑下沉到 BZPlayerCore（无 UI/无 AVFoundation 依赖）：设置编解码与规范化、播放列表排序/循环推进、进度节流判断、字幕候选排序 | 可测试、VM 减负 |
| B | 抽出 `SettingsStore`（全局+文件级+最近文件）、`SubtitleController`、`WindowController`、`MediaAnalysisService` | VM 只做协调 |
| C | 定义 `PlaybackBackend` 协议，把 AVPlayer 逻辑抽成 `NativePlaybackBackend`，与 `VLCPlayer` 对齐；generation 管理上移到协调层 | 后端可替换、可测试 |
| D | 按状态域拆 `@Published`（播放状态 / UI 设置 / 文件信息），减少无谓视图刷新 | 性能与可维护性 |

> 注意：`VLCPlayer.swift` 中大量 VLCKit 4 alpha 的 workaround（重建 player、samplebufferdisplay vout、stop 等待、rate 需 play 后重设）在重构中**必须保留**，并在协议实现处保留来源注释。

### P0-2 测试覆盖严重不足（3 个测试 / 47 行）

**证据**

- 主 target 8087 行代码，**零测试**；CI 中的 `swift test` 只验证 Core 里 3 个纯函数。
- 高风险且**适合补测**的区域：
  - 字幕解析与 cue 二分查找（[ExternalSubtitleRenderer.swift](file:///Users/x/code/bzplayer-main/macos/BZPlayer/Sources/BZPlayerApp/Utils/ExternalSubtitleRenderer.swift)，SRT/VTT/ASS 三格式，纯逻辑）
  - 设置编解码与规范化（`normalizeSpeed` / `normalizeKeyCode` / `clampSubtitlePosition` 等，已被 `AppSettings` 的自定义 `init(from:)` 处理为容错解析）
  - 进度保存节流（`saveCurrentProgressIfNeeded` 的时间/位置双阈值）
  - 播放列表推进（`moveInPlaylist`、loopMode 三态）
  - ffprobe 摘要解析（已有 3 个测试，可继续扩充边界值）

**建议**

- 优先把上述纯逻辑移到 BZPlayerCore，再用 XCTest 覆盖；目标：先补 20–30 个用例覆盖字幕解析与设置容错。
- CI 增加覆盖率采集（`swift test --enable-code-coverage`），先只报告不设门槛，稳定后再设"不得下降"。

### P0-3 fileSettings.json 无界增长，写入放大

**证据**

- 本机现状：**936 条 / 131 KB**，仅 8 月至今就积累至此。
- 写入路径：`saveCurrentProgressIfNeeded()`（节流 5 秒或位移 5 秒）→ `saveFileSettings(for:)` → 加载**全量字典**、改一条、`JSONEncoder` 序列化**全量 131 KB** → 入队写盘。
- **无任何清理/上限逻辑**（对比：recentFiles 有 10 条上限，openedFiles/completedFiles 无）。
- 附带发现：设置目录存在 0 字节 `fileSettings.json.sb-*` 残留文件（疑似原子写/沙盒写残留），值得排查。

**影响**

- 长期使用后：每次保存的序列化成本线性增长；文件持续膨胀；启动加载变慢。
- 对 SSD 造成不必要的写放大（播放中每 5 秒一次全量写）。

**建议**

- 加**条目上限 + LRU 淘汰**（例如保留最近 1000 个文件；`FileSettings` 增加 `lastAccessedAt` 字段），加载时自动 compact 一次。
- 播放中保存降低频率或改为"仅写变化"的分片文件，退出时合并；或将 5 秒节流收紧为 30 秒 + 关键时机（暂停/退出/切换文件）强制写。
- 清理 `.sb-*` 残留：确认写入方式（是否被系统沙盒/编辑器类工具 lock），必要时改为显式临时文件 + rename。

### P1-4 版本管理不一致（与"每次 +0.0.1、满十进一"规则冲突）

**证据（2026-09-29 实测）**

- CI：`version = GITHUB_RUN_NUMBER - 1`，且由 CI **自行创建并推送 tag**（`softprops/action-gh-release`）。当前 tag 已到 `v240`，仓库共有 201 个 tag。
- **跳号明显**：tag 序列缺失 v1–v8、v12、v66–v70、v85–v89、v94–v97、v139、v158–v160、v222–v232 等段——因为 run number 统计所有 workflow 运行（含失败/取消/重跑），版本号不等于"第几次有效修改"。
- 本地安装：[install_macos_app.sh](file:///Users/x/code/bzplayer-main/scripts/install_macos_app.sh#L26-L33) 取"本地最近 tag"作为版本号，变量名 `NEXT_VERSION` 但**不递增、也不打新 tag**，且依赖本地是否 fetch 过 tags。实测：本机已安装应用版本为 `239`，而 CI 最新 Release 已是 `240`，两者已错位。
- 两种机制都未体现"每次修改 +0.0.1、满十进一"（当前版本是单一整数，无 major.minor.patch 结构）。

**建议**

- 建立**单一版本源**（二选一）：
  - 方案 A（推荐）：仓库内维护 `VERSION` 文件，安装脚本与 CI 都读它；发布脚本按规则递增（进位口径待确认，例如 0.0.9 → 0.1.0）。
  - 方案 B：仅以 git tag 为准，由发布脚本递增并打 tag、push；CI 从 `github.ref_name` 取版本，去掉 `RUN_NUMBER - 1` 逻辑。
- 无论哪种方案，都要保证三点一致：本地 `.app` 版本 == CI Release 版本 == git tag。

### P2-8 本地化方案（自定义字典 vs 系统方案）

- 现状：`Localization.swift` 728 行自定义 `t()` 字典查询，7 语言；优点是集中可控，缺点是**无格式校验、无复数/占位符检查、Xcode 工具链无法校核**。
- 建议：暂不迁移（收益/成本比一般）；若后续语言继续增多，再评估 `.xcstrings`。可在 SettingsView 之外增加一个"语言键完整性"测试作为低成本兜底。

### P2-9 CI 可优化点

| 项 | 现状 | 建议 |
|----|------|------|
| VLCKit 缓存 | 每次 CI 重新下载 861 MB（实测最近一次完整 CI 约 4 分钟，含下载） | `actions/cache` 缓存 `.cache/VLCKit-*.zip`（key 含版本+SHA），进一步缩短构建 |
| 发布策略 | 每次 push main 都自动生成新 tag + Release（v237–v240 均为近期自动发布，tag 已累计 201 个） | 改为仅在手动 `workflow_dispatch` 或打 tag 时发布，普通 push 只构建+测试 |
| 并发控制 | 连续 push 会并发触发多组构建 | 增加 `concurrency` 组，自动取消旧构建 |
| 依赖 action 版本 | `softprops/action-gh-release@v2.3.3` 被 GitHub 注解 Node.js 20 弃用警告 | 升级到最新版本 |
| 代码规范 | 无 lint/format 检查 | 引入 SwiftLint（先仅报告）|
| 覆盖率 | 无 | `--enable-code-coverage` + 报告 |
| 构建矩阵 | 仅 macos-latest | 如需 Intel 支持可加 x86_64 构建（当前产物为 runner 架构） |

### P2-10 分发准备

- 签名/公证：CI 已实现（条件触发），但 secrets 未配置时产物 unsigned，用户首次打开需手动放行。
- 无自动更新（可评估 Sparkle）。
- 未启用 App Sandbox（上架 Mac App Store 才需要；独立分发可不做，评估即可）。

### P2-11 功能缺口（供决策，不建议全做）

按"投入产出 + 与播放器定位匹配度"粗排：

1. **网络流播放（URL / m3u8 / HLS）**：AVPlayer 原生支持，工作量小；如需可加"打开 URL"入口。与本地播放器定位相关的决策点。
2. **截图（当前帧导出 PNG）**：爱好者向播放器常见需求，中等工作量。
3. **A-B 循环**：学习场景常用，工作量小（在现有 seek/进度体系上扩展）。
4. **PiP（画中画）**：AVPlayer 侧原生支持，VLC 侧需自绘，建议仅原生后端开启。
5. **播放列表拖拽排序 / m3u8 导入导出**：中等工作量。

## 五、重构红线（务必遵守）

1. **保留 VLCKit 4 workaround 与 generation 竞态机制语义**，重构只搬位置不改行为。
2. 每步重构前备份 `~/Library/Application Support/BZPlayer/`（用户规则）。
3. 回归清单（每步重构后手动验证）：mkv+h264、mp4+av1、mp4+vp9、外挂字幕、音频延迟、后端切换、seek、16x 倍速、audio-only 最小化、多窗口。
4. 版本号按用户规则递增；重构不考虑旧数据兼容，但需自动迁移或明确重置路径。
