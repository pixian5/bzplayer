## 一、本轮动机

对上一轮引入的 `MP4ContainerInspector`（手写 ISO BMFF 解析）与 `resolveBackend` 再做一次只读审查，发现 6 个问题：其中 **1 个是崩溃级**（整数溢出直接 trap 进程），**2 个是误判级**（会误伤本应走原生的静音 MP4），**1 个是性能级**（同一文件被解析两遍），**2 个是健壮性/覆盖级**。

它们都只在 **ffprobe 缺失**这条兜底路径上暴露，而这条路径恰恰是普通用户（没 `brew install ffmpeg`）的默认路径，因此优先级不低。

## 二、六项修复

| # | 级别 | 问题（修复前） | 修复 |
|---|---|---|---|
| 1 | **崩溃** | `walk` 里直接算 `cursor + header.size`。当 64 位 `largesize` 接近 `Int.max` 时**整数溢出**，Swift 溢出即 trap，整个播放器崩溃（实测 `exit=133` / SIGTRAP） | 改为**先比较再相加**：`guard header.size <= end - cursor` 通过后才 `boxEnd = cursor + header.size` |
| 2 | **误判** | `readBoxHeader` 一次性 `read(at:count:8+8)` 读 16 字节。文件末尾那种**只有 8 字节头、没有 payload** 的小 box（`free`/`skip` 填充）会读取越界返回 `nil`，被判成"结构异常"→ `.unknown` → 保守走 VLC，**误伤本就无音轨的静音 MP4** | 先只读 8 字节基础头；仅当 `size == 1` 时再补读 8 字节 `largesize` |
| 3 | **误判** | `mp4FamilyAudioNeedsVLC` 里 `guard let audioTracks = try? await asset.loadTracks(...) else { return false }`：`loadTracks` 抛错（文件损坏、权限、扩展名伪装等）时**默认"不需要 VLC"**，与旁边"容器解析失败 → 保守走 VLC"的策略**自相矛盾**，可能静音 | 改为 `return true`。统一策略：**无法判定 → 宁可功耗略高，不可静音** |
| 4 | **性能** | 播放路径先 `chooseBackend(...)` 选后端，之后又用**新的** `AVURLAsset` 调一次 `hasAV1Video(url:)`。ffprobe 缺失时同一文件被 AVFoundation 解析两遍 | 新增 `BackendChoice { backend, hasAV1 }` 与 `resolveBackend(...)`：一次解析同时产出两者，`probedHasAV1` 缓存 `decide` 内部已算出的结果；`chooseBackend` 退化为便捷包装，文件信息面板等既有调用点无需改动 |
| 5 | 覆盖 | 手写解析器的**边界情况零覆盖**：末尾 8 字节 box、64 位 `largesize`、`size == 0`、超大 size 溢出防护 —— 上面 1、2 两个缺陷正是因此逃过上一轮 | 补 5 个边界单测（见第四节） |
| 6 | 健壮性 | `hdlr` 分支读 `bodyStart` 起 12 字节前**没校验 box 内是否真有 12 字节**。截断的 `hdlr`（如只声明 8 字节头）会读到**下一个 box 的字节**，若那里恰好是 `soun` 就误判成音频轨 | 加 `boxEnd - bodyStart >= 12` 限界后再读 |

## 三、修复 1 与 2 的细节

### 溢出（修复 1）

```swift
// 修复前：cursor + size 可能溢出 Int → trap
let boxEnd = cursor + header.size

// 修复后：先判剩余空间，再做加法
let boxEnd: Int
if header.size == 0 {
    boxEnd = end            // size == 0：合法写法，延伸到 EOF
} else {
    guard header.size <= end - cursor else { state.malformed = true; return }
    boxEnd = cursor + header.size
}
```

顺带把 `headerLength` 与 `bodyStart` 也做了同样的"先比较再相加"处理，避免 16 字节头的 `largesize` box 在缓冲区尾部再次越界。

### 末尾 8 字节 box（修复 2）

`readBoxHeader` 现在分两段读：

```swift
guard let base = source.read(at: offset, count: 8), base.count == 8 else { return nil }
var size = Int(readUInt32(base, at: 0))
var headerLength = 8
if size == 1 {                       // 只有声明 largesize 时才再读 8 字节
    guard let extra = source.read(at: offset + 8, count: 8), extra.count == 8 else { return nil }
    let large = readUInt64(extra, at: 0)
    guard large <= UInt64(Int.max) else { return nil }
    size = Int(large)
    headerLength = 16
}
```

这条修复的实际影响：`ffmpeg` 产出的 MP4 常在 `moov` 尾部或文件末尾带 `free` 填充 box，尺寸恰好 8 字节。修复前这类**完全合法**的文件会被判 `.unknown`，于是每次播放都退回 VLC —— 静音问题解决了，但白白丢掉了 AVPlayer 的硬件解码与省电收益。

## 五、取舍与残留

- `.unknown` 与 `loadTracks` 抛错一律走 VLC：**功耗换确定性**。仅在 ffprobe 缺失时可能触发，且只影响"疑似有音频但读不出来"的极少数文件。
- `resolveBackend` 在 `decide` 短路（如 mkv 早退）时仍会补一次 AV1 探测，因为 `currentMediaHasAV1Video` 是 UI 侧的独立需求。此处的探测复用同一个 `AVURLAsset` 实例，代价已被 AVFoundation 实例内缓存摊薄。
- 未覆盖：`hasVideoDecodeErrors`（h264 解码错误扫描）的异步逻辑仍无单测；MP3-in-MOV、ADPCM 等其它"容器 × 编码"组合未实测。
