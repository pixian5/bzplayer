## 二、六项修复

| # | 问题（修复前） | 修复 |
|---|---|---|
| 1 | **ffprobe 缺失时的兜底判据太粗**：用"MP4 系列容器 + AVFoundation 音轨为空"作信号，会把**本就无音轨的静音 MP4**也判去 VLC，丢原生硬件解码、抵消 AV1 省电策略 | 新增 `MP4ContainerInspector`：直接解析 MP4 容器的 `moov/trak/mdia/hdlr`，看 `handler_type` 是否为 `soun`。判据改为「**容器声明了音频轨，但 AVFoundation 取不到音轨**」才走 VLC；容器未声明音频 → 保持原生 |

## 三、关键设计：读容器字节区分"本来无音轨"与"音轨被丢弃"

问题 1 的核心难点：AVFoundation 对 MP3-in-MP4 是**静默丢轨**（`audioTracks == 0` 且 `isPlayable == true`），所以单看 AVFoundation 无法区分：

- 文件**本来就没有音轨**（如无声录屏）→ 应保持原生省电；
- 文件**有音轨但被丢弃** → 必须交给 VLC。

解法是绕开解码器，直接看容器自己的声明：ISO BMFF 里每条轨道是 `moov → trak → mdia`，`mdia → hdlr` 的 `handler_type` 为 `soun` 即音频轨。只读 box 头部并按 size 跳过，**不把文件读进内存**，对 GB 级文件也几乎是常数开销。

`MP4ContainerInspector.audioTrackPresence` 返回三态：

- `.declared`：容器有 `soun` → 但取不到音轨 → 被丢弃 → 走 VLC；
- `.none`：容器没有 `soun` → 本来无音轨 → 保持原生；
- `.unknown`：结构异常/解析失败 → **保守走 VLC**（宁可功耗略高，不可静音）。

## 五、取舍与残留

- `.unknown` 保守走 VLC：解析失败时宁可功耗略高，也不冒静音风险；仅在 ffprobe 缺失时可能触发。
- 未覆盖：`hasVideoDecodeErrors`（h264 解码错误扫描）异步逻辑；MP3-in-MOV、ADPCM 等其它"容器×编码"组合。
- CI 版本仍用 `GITHUB_RUN_NUMBER - 1`，与本机 `VERSION` 不同源；统一 CI 会让"仅改文档未递增版本"的提交造成 tag 冲突，故本轮不动，留待明确方案。
