# 构建发布与版本号

## 1. 三个脚本的职责

| 脚本 | 作用 | 关键点 |
|---|---|---|
| `scripts/fetch_vlckit.sh` | 下载/校验 VLCKit 到 `macos/Vendor/vlckit-spm/` | 校验 `VLCKIT.lock`（版本/URL/SHA/大小） |
| `scripts/build_macos_app.sh` | 打包 `.app` | 用法 `build_macos_app.sh <输出.app> <版本号> <构建目录>` |
| `scripts/install_macos_app.sh` | 安装到 `/Applications` 并启动 | 结束旧进程 → 重建 → `lsregister` → `open` |
| `deploy.sh` | 部署封装（支持 `--commit`） | 中文提交并 push `origin main` |

【结论】打包脚本会把 `VLCKit.framework` 复制进 `Contents/Frameworks`，并给可执行文件写 `@executable_path/../Frameworks` rpath，最后 `plutil -lint` 校验 `Info.plist`。
【避坑要点】**只拷贝 release 二进制不行**；必须用这两个脚本，否则 VLCKit 加载不到。
【依据/来源】`scripts/build_macos_app.sh` L85-108。

## 2. 安装脚本的版本来源与提交

【结论】`install_macos_app.sh` 的版本号**读取仓库根目录 `VERSION` 文件**（2026-10-17 起；此前用 `git describe --tags --abbrev=0` 取本地最近 tag）。变量名 `NEXT_VERSION` 但**不递增、也不打新 tag**。
【避坑要点】它**默认不提交**；只有 `install_macos_app.sh --commit "中文说明"` 或 `./deploy.sh --commit "中文说明"` 才 `git add -A` + commit + push。
【依据/来源】`scripts/install_macos_app.sh` L25-38。

## 3. GitHub Actions（CI）

【结论】工作流 `.github/workflows/build-and-release.yml`：push `main` 或手动 `workflow_dispatch` 触发；流程 = fetch VLCKit → `swift build -c release` → `swift test` → 打包 `.app` → （可选签名/公证）→ 建 DMG → 上传 artifact → **自动创建 tag 并发布 Release**。
【避坑要点】CI 版本规则（2026-10-17 起）：
- `version` = **读根目录 `VERSION` 文件**（与本地安装脚本同源）；
- `tag` = `v${VERSION}-${YYYYMMDD}-${HHMM}`（**东八区 Asia/Singapore** 时间戳），由 `softprops/action-gh-release@v2.3.3` 自行创建。
- **为什么 tag 要带时间**：`VERSION` 只在改源码时递增，仅改文档的提交会沿用同一 `VERSION`；若 tag 只含版本号，同一分钟内**第二次 push 就会撞上已存在的同名 tag**，Release 步骤失败、CI 变红。带时间戳后每次 push 都是唯一 tag。
- 旧规则曾是 `version = GITHUB_RUN_NUMBER - 1`（统计**所有** workflow 运行，含失败/重跑 → tag 跳号）。
- **残留边界**：时间戳精确到分钟，**同一分钟内连续两次 push 仍可能撞名**；彻底避免可再追加 run number（如 `v244-20261017-0206-123`）。
- 连续 push 可能并发触发多组构建（文档建议加 `concurrency` 取消旧构建）。
【依据/来源】`.github/workflows/build-and-release.yml` L33-49、L140-147；分析文档 P1-4。

## 4. 版本号来源（2026-10-17 已统一）

【结论】**单一版本源 = 仓库根目录 `VERSION` 文件**，本地与 CI 都读它：
| 来源 | 机制 | 说明 |
|---|---|---|
| 根 `VERSION` 文件 | 手工递增（改源码 +0.0.1） | **唯一版本源** |
| 本地 `/Applications/BZPlayer.app` | 安装脚本读 `VERSION` | 版本串 = `VERSION` |
| CI 构建产物（.app / DMG） | 读 `VERSION` | app 版本串 = `VERSION` |
| CI Release **tag** | `v${VERSION}-${时间戳}` | tag 额外带时间以保证唯一 |
【避坑要点】
- 打包脚本传给 `CFBundleShortVersionString` 的**必须是纯数字**（Apple 要求 1–3 个点分整数），所以**时间戳只加在 tag 上，不能写进 app 版本串**。
- 只改文档的提交**不递增** `VERSION`：tag 靠时间戳区分，app 版本串保持不变（这正是预期行为）。
【依据/来源】`scripts/install_macos_app.sh`、`.github/workflows/build-and-release.yml`、`scripts/build_macos_app.sh` L69-72。

## 5. 签名与公证现状

【结论】本地安装与 CI 产物**默认 unsigned**：CI 仅在配置 `MACOS_CERTIFICATE_BASE64`/`MACOS_CERTIFICATE_PASSWORD`/`MACOS_SIGNING_IDENTITY` 后 `codesign`；再配置 `APPLE_API_KEY_*` 才 `notarytool submit` + `stapler staple`。
【避坑要点】secrets 未配置时用户首次打开需手动放行；生产分发前应补 Developer ID 签名 + 公证 + staple。
【依据/来源】CI L67-113 与 `readme.md` 重大说明。
